# M10.3 subject analysis and mappings

M10.2 is present: migration 16, `src/motion/source-import.ts`, source videos and frame-aligned segments. Core code is flat under `src/`, so this feature lives in `src/motion/`, with no Electron imports.

Migration 17 (`src/motion/017-subjects-migration.ts`, Motion subjects and owner mappings) uses the existing transactional runner. Adds subjects, mappings, segment analysis JSON and `source_videos.face_consent`, default false. Rights confirmation is distinct from face consent. An owner can explicitly update face_consent in the DB; keep and preflight both check it. Segment insertion now names its columns to support the added analysis column.

Public API (exported from `src/motion/index.ts`):

- `analyzeSubjects(db: DatabaseSync, sourceVideoId: string, options: AnalyzeSubjectsOptions): Promise<MotionSubject[]>`
- `listSubjects(db: DatabaseSync, sourceVideoId: string): MotionSubject[]`
- `setMapping(db: DatabaseSync, subjectId: string, target: string): MotionMapping`
- `getEffectiveMapping(db: DatabaseSync, subjectId: string): MotionMapping | undefined`
- `validateMappings(db: DatabaseSync, sourceVideoId: string): void`
- `loadMotionPresets(): Record<string, string>`
- `compileMotionSegment(db, segmentId, bible: CompilerBible, {preset, maxReferenceImages, presets?}): CompiledScene`

Analysis uses M3 extractFrame (injectable) and M4 generateValidated/schema validation. The local CLI receives image paths in the prompt to inspect with its vision tools. Providers must support inspecting local images. Samples cover start, middle, last frame; count is configurable 1–20. Strict output includes subjects, motion, rhythm and composition; prose requests appearance, camera and lighting. Duplicate subject keys are rejected. Each segment commits atomically after validation. Keys are stable within segments; prior subjects are included for cross-segment consistency, which remains a model proposal rather than a guaranteed identity tracker.

AI defaults are conservative: faceless for visible human faces, otherwise keep. Raw suggestions remain in subjects; a unique mapping row is updated only if AI-owned. Owner rows are never overwritten, including during reanalysis. Subjects absent in a later response remain retained so owner decisions are not deleted. Re-segmenting explicitly replaces segments and cascades their analysis/mappings.

Mappings reuse M2 parser, validation and Bible lookup, scoped to the source project. Character and location registrations map to character/scene. Preflight re-resolves references and checks stored identity and role, catching deletions, renames and consent revocation before downstream work. No job, Flow call or credit record is created here. Future preview/render entry points must call validateMappings before creating work. Failed mapping requests are not persisted; preflight validates existing persisted mappings, not rejected requests.
