# M10.1: Flow video editing and frame images

The existing M5 implementation is extended, without a second browser driver or queue.

- Adapter and verification stop: `src/flow/driver.ts` (`ActionRecorder.guard`). Account status is written by `src/flow/accounts.ts`; verification sets `needs_owner`.
- Selector configuration: `src/flow/selectors.ts`, with the existing JSON override at `config/flow-selectors.json`.
- Selftest and command: `src/flow/selftest.ts`, `src/flow/cli.ts`.
- Fake page: `src/flow/mock/index.ts`, re-exported by `test/support/flow-fake/index.ts`.
- Browser availability: `test/support/browser.ts`. Media discovery and execution: `src/media/discovery.ts`, `src/media/runner.ts`; existing test helpers: `test/helpers/media.ts`.

## Public API

```ts
editVideo(job: VideoEditJob, ctx: FlowDriverContext): Promise<MotionResult>
generateFrameImage(job: FrameImageJob, ctx: FlowDriverContext): Promise<MotionResult>
motionSelectors(profile: SelectorProfile): Selectors
```

Jobs use an existing queue job ID, project ID and account ID. `VideoEditJob` adds `sourceVideo`, `variants` (K), and optional `references`, a map of role to image paths. Roles are `character`, `setting`, `style`, `first_frame`, `last_frame`. `FrameImageJob` adds `frameKind` (`first_frame` or `last_frame`) and the same optional references. Prompt and output directory are inherited from `FlowJob`; timeout is `ctx.timeoutMs`.

Inputs must resolve inside the project, including symlink targets. Output must be the project's `renders/` directory or a child. Output filenames are `<jobId>_edit_<1-based index>.mp4` and `<jobId>_<frameKind>_1.png`. Existing outputs are rejected before submission. Downloads use temporary `.partial` files, following M5. A completed result returns `files`, `creditsBefore`, `creditsAfter`, `creditsCharged`, `durationMs` (elapsed operation time), and `accountId`. Failures use M5's typed result kinds. Callers own browser cleanup.

## Selector configuration

Groups use dotted names in M5's existing flat selector map:

- `videoEdit`: `entry`, `video`, `prompt`, `variants`, `submit`, `progress`, `finished`, `download`, plus all five reference roles.
- `frameImage`: `entry`, `kind`, `prompt`, `submit`, `progress`, `finished`, `download`, plus all five reference roles.

The shared `verify-challenge`, credit counter and error banner are reused. Selftest checks every new name even if a supplied selector map omits it; omitted/empty values report `chua_dien`, invalid/not-found values report `hong`, and CLI exits 1 on failure. Hidden inventory controls on `/selftest` allow all states to be checked without paid generation.

The provided task workspace does not include `config/flow-selectors.json` and disallows creating files outside the context directories. Consequently the new defaults are declared in the existing selector configuration module and merged with the existing JSON values; JSON entries can override them. No parallel config file was created. All real `videoEdit.*` and `frameImage.*` values are empty with owner calibration notes. The owner must fill every listed control in the existing real profile, then run `flow selftest --profile real --url <Flow URL>`.

## Fake contract

`FAKE_FLOW_PRICES = { videoEdit: 12, frameImage: 2 }`: credits per video variant and per image respectively. K variants deduct K times the video price. The fake balance is shared with the existing mode. Uploaded bytes and grouped references are available in fake state for assertions; they are never action-log values.

`FAKE_FLOW_WATERMARK = { x: 272, y: 216, width: 40, height: 16 }`, on 320x240 media, is an opaque white rectangle at bottom right. M10.6 can import this constant. Both videos and frame PNGs use this marker. These are synthetic fixtures, not an assertion about production Flow watermark geometry. New modes require ffmpeg; the old mode retains its existing runtime MP4 fallback. Temporary fake files live under `VIDFLOW_HOME` when set and are cleaned on close.

`setScenario({ verification: true })` shows verification before entry. An `onGenerate` callback can enable verification after submission; polling reloads into the challenge. No bypass is attempted. Action logs contain symbolic names only; no screenshots, storage state or authentication values are recorded by the new actions. Verification results omit the page address.
